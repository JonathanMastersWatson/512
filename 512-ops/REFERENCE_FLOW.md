# Reference Flow

This document describes the end-to-end sequence of events from
intent declaration to anchored evidence for a system satisfying
512's properties at the execution boundary.

Read this document to understand what happens at each stage,
what is produced, and what the gate and witness layer observe.

---

## The Sequence
INTENT → PROPOSAL → EVALUATION → COMMIT AUTHORISATION → EXECUTION → EVIDENCE → ANCHOR

Each stage is described below.

---

## Stage 1 — Intent

An agent or system declares what it intends to do.

Intent is upstream of the gate. The gate does not evaluate intent
as a raw statement — it evaluates a structured Proposal Object
constructed from that intent.

**What happens at this stage:**
- the proposing entity determines the action it wants to take
- the action type is classified against the controlled vocabulary
- the proposing entity's authorisation token is prepared

**What the gate sees:** nothing yet. The gate is not involved
until a Proposal Object arrives.

**What the witness layer sees:** nothing yet.

---

## Stage 2 — Proposal Construction

The proposing entity constructs a Proposal Object before the
commit boundary is crossed.

The Proposal Object is the gate's only input from the proposing
entity. It must be constructed completely before evaluation begins.
It is not reconstructed after the fact.
{
proposal_id:          unique identifier generated by proposing entity
agent_id:             cryptographically attested identity
action_type:          from controlled vocabulary
action_params:        scoped parameters of the proposed action
declared_scope:       bounds the proposing entity declares it will not exceed
consent_evidence:     explicit consent token for each affected party
contract_reference:   identifier of the governing terms
exit_available:       boolean — confirmed before construction
rules_disclosed:      boolean — active constraint set disclosed to parties
spec_hash:            SHA-256 of the active constraint set
authorisation_token:  cryptographic proof of authorisation
intent_hash:          SHA-256 of the serialised intent
timestamp:            ISO 8601 — gate's clock governs, not proposer's
}

**What the gate sees:** the completed Proposal Object arrives
at the boundary.

**What the witness layer sees:** a pre-validation event is emitted
immediately after the Proposal Object is received and the
authorisation token is verified. This is Observation Point 1.

---

## Stage 3 — Evaluation

The gate evaluates the Proposal Object against all seven invariants.

Evaluation is deterministic. Identical inputs produce identical
outputs on every invocation. No external I/O occurs during
evaluation. No human judgment is applied.

Each invariant produces a binary result: pass or fail.
I1 — No force or fraud             pass / fail
I2 — Explicit consent              pass / fail
I3 — Consent withdrawal available  pass / fail
I4 — Contractual clarity           pass / fail
I5 — No hidden rules               pass / fail
I6 — Fail-open confirmed           pass / fail
I7 — Immutability and binary sat.  pass / fail

If all seven pass: overall result is ALLOW.
If any fail: overall result is DENY, with the specific
violated invariant identified.
If the gate cannot complete evaluation: the gate produces no output. Execution proceeds under fail-open. The witness layer records the ungoverned period as an evidence chain gap.

**Evaluation completes in under 50μs (median) in software.**
**Under 5μs on dedicated hardware.**

**What the gate sees:** the full evaluation completes synchronously.

**What the witness layer sees:** a validation-result event is
emitted after evaluation completes. This is Observation Point 2.
It contains the overall result, per-invariant results, the spec
hash, and evaluation duration.

---

## Stage 4 — Commit Authorisation Signal

The gate returns exactly one of two values.

### ALLOW
All seven invariants passed.
The commit path opens.
Execution may proceed to irreversible state change.

The gate appends no conditions, recommendations, or caveats
to an ALLOW result. ALLOW means the commit path opens. Nothing more.

### DENY
One or more invariants failed.
The commit path remains closed.
Execution does not proceed.
The violated invariant identifier and deny message are returned.

The proposing entity is informed which invariant failed and why.
No guesswork. No ambiguity.

### Fail-Open (Gate Unavailable)
The gate was unavailable or evaluation timed out.
The gate produces no output — evaluation did not complete.
The commit path opens because fail-open behaviour is engaged.
Execution proceeds.

This is not an ALLOW. Constraint satisfaction was not established.
The fail-open handler emits a gap record to the witness layer.
The gap is recorded and must not be concealed.

The witness layer — not the gate — classifies this as an evidence
chain gap. The gate's absence from the signal path is itself the
evidence of the ungoverned period.

**The gate's signal is the structural prerequisite for the commit
path to open. It is not advisory. It is not delivered to a
downstream layer for interpretation or application.**

---

## Stage 5 — Execution

The action crosses the commit boundary and becomes an irreversible
state change.

This stage is outside the gate. The gate has no involvement in
execution. The gate permitted or denied the proposal. What happens
at the execution surface is the implementation's responsibility.

**Intent-execution correspondence:** the execution layer must
enforce that actual execution does not exceed the declared scope
in the Proposal Object. The gate evaluated declared intent.
If execution exceeds declared intent, the gate's allow result
has been exploited.

**What the gate sees:** nothing. The gate's involvement ends
at Stage 4.

**What the witness layer sees:** a post-execution event is emitted
after execution completes. This is Observation Point 3. It contains
the actual execution outcome and the actual scope of what executed.

---

## Stage 6 — Evidence Assembly

The witness layer assembles the three observation point events
into a complete Evidence Object for this proposal.
Evidence Object
├── pre_validation          (Observation Point 1)
│   ├── proposal_id
│   ├── agent_id
│   ├── intent_hash
│   ├── authorisation_token_hash
│   └── timestamp
│
├── validation_result       (Observation Point 2)
│   ├── overall_result      ALLOW or DENY (absent on fail-open events — see gap_record)
│   ├── spec_hash
│   ├── per_invariant_results
│   ├── violated_constraint_detail  (on DENY only)
│   └── evaluation_duration_us
│
└── post_execution          (Observation Point 3)
├── execution_outcome   completed / failed / cancelled
├── actual_scope
└── execution_duration_us

The three observation points are linked by a common correlation ID.

Each Evidence Object is hash-chained to the previous: the hash
of the prior Evidence Object is included in the current one.
Modification of any Evidence Object breaks the chain at that point
and propagates forward — detectable by any verifier.

---

## Stage 7 — Anchor

The witness layer computes a Merkle root over a batch of Evidence
Objects and anchors it to the XRP Ledger.
Evidence Object N-2  ─┐
Evidence Object N-1  ─┤─► Merkle Root ─► XRPL Transaction
Evidence Object N    ─┘                   └── tx_hash (public, permanent)

**What is anchored:** the Merkle root only. No proposal content,
no personal data, no contract text. Hashes only.

**What this proves:** any Evidence Object in the batch can be
independently verified against the anchored Merkle root by any
party with access to the public ledger — no operator cooperation
required.

**Anchoring frequency:** every 30 seconds under standard
configuration. Evidence Objects generated before the next
anchoring window are locally persisted and included in the
next batch.

**XRPL anchor transaction from genesis:**
`378536A3CB75DECF90B6AE57F75292BDFF716285B01946870CAC158F8152D100`

## What This Flow Does Not Cover

This flow describes the execution and evidence path only.

It does not cover:
- constraint definition (upstream of Stage 2 — see
  `512-ops/CONSTRAINT_DEFINITION_LAYER.md`)
- gate construction (see `512_IMPLEMENTATION`)
- witness layer construction (see `CVS_ARCHITECTURE`)
- regulatory interpretation of evidence records
